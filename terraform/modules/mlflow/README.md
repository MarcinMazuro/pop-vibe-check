# modules/mlflow

Runs the MLflow tracking server (`mlflow_server/`) as a Cloud Run service behind Identity-Aware Proxy, with run metadata and the model registry in Cloud SQL Postgres. Artifacts stay in GCS under `nlp/mlruns/` on the artifacts bucket. Why it is shaped this way: [ADR 0004](../../../docs/adr/0004-mlflow-tracking-server-on-cloud-run-and-cloud-sql.md).

## What this creates

- **`{name_prefix}-mlflow-{env}`**: a Cloud SQL Postgres 16 instance, Enterprise edition, `db-f1-micro`, zonal, 10 GB SSD with autoresize, 7 daily backups, deletion protection on. It has a public IP with **no authorized networks**, so only the Cloud SQL connectors can reach it, and they authenticate with IAM. **It runs permanently and is this module's standing cost.**
- **Database `mlflow`** and **user `mlflow`**. The password is generated by Terraform (`random_password`) and stored in the secret **`{name_prefix}-mlflow-{env}-db-password`**. Unlike the external credentials in `modules/secrets`, it originates here, so it is in Terraform state.
- **`{name_prefix}-mlflow-{env}`**: a Cloud Run v2 service running as the MLflow SA. 1 CPU, 1Gi, 0–1 instances, one worker. It reaches the database over Cloud Run's built-in Cloud SQL connection (`/cloudsql`) and runs `--no-serve-artifacts`, so clients write artifacts to GCS themselves. It is created on Google's public `hello` image; Cloud Build deploys the real one, and the image field is ignored afterwards.
- **For the MLflow SA**: `roles/cloudsql.client` on the project and `roles/secretmanager.secretAccessor` on the password secret. Read access to `nlp/mlruns/` comes from `modules/storage`, next to the bucket.
- **`roles/run.invoker`** on the service for the IAP service agent.
- **`roles/iap.httpsResourceAccessor`** on the project for each of `client_sa_emails` (the Workbench trainer). People are not granted anything here: the project-level grant `modules/dashboard` makes for `report_viewer_emails` already covers every IAP resource in the project.
- **Image deployer grants** (when `deployer_sa_email` is set): `roles/run.developer` on the service and `roles/iam.serviceAccountUser` on the MLflow SA.

## First deployment

1. **The Cloud SQL Admin API and the runner's role.** Both are in `terraform/bootstrap/`. Bootstrap's state is not on every laptop, so grant them by hand and keep the bootstrap files in sync:

   ```bash
   gcloud services enable sqladmin.googleapis.com --project=pop-vibe-check
   gcloud projects add-iam-policy-binding pop-vibe-check \
     --member=serviceAccount:pvc-tf-runner-sa@pop-vibe-check.iam.gserviceaccount.com \
     --role=roles/cloudsql.admin --condition=None
   ```

2. **Apply** through the usual PR, merge and approved `co-terraform-apply-dev` build. The instance takes about ten minutes to create.

3. **The first image.** The deploy trigger is created by that same apply, so the merge commit itself did not build anything. Build once by hand (the command is in `mlflow_server/cloudbuild.yaml`), or let the next change under `mlflow_server/` do it.

4. **IAP.** Provider 5.x cannot set it, so it is switched on once, as for the dashboard:

   ```bash
   gcloud run services update co-mlflow-dev --region=europe-central2 --iap
   ```

   The project's custom OAuth client and its test-user list are shared with the dashboard. Anyone who can open the dashboard can open MLflow.

5. **Check the server.** Open `terraform output mlflow_url` in a browser and you should get the MLflow UI after the Google sign-in.

## Logging runs from Workbench

The trainer SA calls the server through IAP with a Google ID token minted for IAP's OAuth client. `nlp/tracking/mlflow_utils.py` fetches the token and refreshes it on a timer when both of these variables are set:

```bash
export MLFLOW_TRACKING_URI=$(terraform output -raw mlflow_url)
# IAP OAuth client ID: Security → Identity-Aware Proxy → settings,
# or APIs & Services → Credentials (the IAP web client).
export MLFLOW_IAP_AUDIENCE=<client-id>.apps.googleusercontent.com
```

Workbench has no public IP. It reaches `*.run.app` over Private Google Access on the subnet.

Copying the runs that predate the server out of the Workbench file store is a one-off job: `python -m nlp.tracking.migrate`; see its docstring.

## Caveats

- **Everyone through IAP can edit.** MLflow has no permissions model in this setup: whoever can open the UI can rename or delete runs. Deleting a run only marks it deleted, and the database is backed up daily.
- **A Terraform change to the service may switch IAP off.** That fails closed: the run.app URL then wants `run.invoker`, which nobody holds. Re-run step 4.
- **Upgrading MLflow.** The server creates its schema on first boot but does not migrate an existing one. When `mlflow_server/requirements.txt` moves to a version with schema changes, run `mlflow db upgrade` against the database first, through the Cloud SQL Auth Proxy with `instance_connection_name`. Raise the training client's upper bound (`nlp/training/requirements.txt`) along with the server.

## Inputs

| Name | Type | Required | Default | Description |
|---|---|---|---|---|
| `project_id` | string | yes | — | GCP project ID |
| `name_prefix` | string | yes | — | Short release prefix (2-8 chars) |
| `env` | string | yes | — | Environment name; suffixed into resource names |
| `region` | string | yes | — | Region of the service and the instance |
| `labels` | map(string) | yes | — | Labels applied to the service, the instance and the secret |
| `mlflow_sa_email` | string | yes | — | Runtime identity of the service |
| `artifact_root` | string | yes | — | Default artifact root, e.g. `gs://co-tf-artifacts-dev/nlp/mlruns` |
| `client_sa_emails` | list(string) | no | `[]` | SAs that call the server through IAP |
| `tier` | string | no | `db-f1-micro` | Cloud SQL machine tier |
| `database_version` | string | no | `POSTGRES_16` | Cloud SQL Postgres version |
| `image_uri` | string | no | `hello` sample | Image the service is created with; ignored afterwards |
| `memory` | string | no | `1Gi` | Container memory limit |
| `cpu` | string | no | `1` | Container CPU limit |
| `deployer_sa_email` | string | no | `null` | Cloud Build SA granted deploy rights; `null` skips |

## Outputs

| Name | Description |
|---|---|
| `service_name` | Short service name, e.g. `co-mlflow-dev` |
| `service_url` | run.app URL: the UI, and `MLFLOW_TRACKING_URI` for clients |
| `instance_connection_name` | `project:region:instance`, for the Cloud SQL Auth Proxy |
